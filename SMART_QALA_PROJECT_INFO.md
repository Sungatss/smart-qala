# Smart Qala — проверенное состояние проекта

Дата анализа: 8 октября 2026 года. Рабочий каталог приложения: smart-qala/. Этот файл фиксирует факты текущего исходного кода для практических работ № 1–15 по ТРПО. Методические указания задают темы и форму отчётов; приведённые в них университет, библиотека, банк и медицинская система являются учебными примерами. В отчётах предметная область едина — Smart Qala.

## 1. Назначение и статус

Smart Qala, в интерфейсе VoiceOfSemey, — демонстрационное веб-приложение для обращений жителей Семея о городских проблемах и для предложений по развитию города. Пользователь может создать обращение или идею, просматривать их, карту и карточки; интерфейс сотрудников позволяет менять данные заявок. Реального подключения к городской инфраструктуре в коде нет.

**Статус на дату анализа:** текущая рабочая копия не проходит TypeScript-проверку и ESLint. Описанные ниже функции существуют в исходниках, но нельзя утверждать, что все пользовательские сценарии сейчас работают в собранном приложении. До подготовки отчётов с формулировкой «работает» необходима повторная проверка после восстановления согласованности контекста.

## 2. Структура и стек

- Приложение: Next.js 16.3.6 с App Router, React 19.2.8, TypeScript 5, Node.js. Пакетные версии взяты из smart-qala/package.json; требование к версии Node.js отдельно в package.json не задано.
- Интерфейс: Tailwind CSS 4, Radix UI, lucide-react, framer-motion, sonner. Словари трёх языков находятся в src/lib/translations.ts; стили и режим повышенной читаемости — в src/app/globals.css и компонентах.
- Карта: Leaflet с тремя конфигурациями тайлов Esri в src/components/CityMap.tsx. Загрузка тайлов зависит от сети и внешнего сервиса.
- Анализ текста: @google/genai и модель gemini-2.5-flash при наличии GEMINI_API_KEY или GOOGLE_API_KEY; при отсутствии ключа либо ошибке вызывается локальный классификатор правил из src/lib/ai-service.ts. Факт успешного внешнего вызова в рамках этого аудита не проверялся.
- Данные: демонстрационные массивы и операции в src/lib/mock-data.ts; постоянной БД, ORM и миграций нет. В сид-наборе 17 обращений, из них 4 идеи. Состояние хранится в globalThis одного серверного процесса и теряется при перезапуске; это не обеспечивает согласованность между несколькими процессами.
- Тестовая инфраструктура: в package.json есть dev, build, start и lint; отдельного test-скрипта и каталога тестов в проекте нет. scripts/screenshot.mjs и screenshot-auth.mjs делают скриншоты, не являются автоматическими тестами бизнес-логики.
- В корне рабочей папки src и package.json являются символическими ссылками на smart-qala/src и smart-qala/package.json. Git-репозиторий находится в smart-qala/.

## 3. Единая предметная модель

Типы определены в src/types/index.ts:

| Сущность / тип | Проверенное содержание |
|---|---|
| CityRequest | Обращение типа problem или idea: текст, категория, ведомство, приоритет, статус, адрес и координаты, медиа-ссылки, голоса, необязательные поля автора, модерации и официальной переписки |
| UserProfile | Профиль с ролью citizen, employee либо admin; guest в типах не отдельная роль, а необязательный флаг isGuest |
| OfficialFeedbackMessage | Сообщение в массиве official_feedback конкретного обращения |
| NotificationItem | Уведомление с типом, ссылкой и признаком прочтения |
| DeveloperFeedback | Сообщение через демонстрационный канал обратной связи разработчикам |
| AIAnalysisResult | Результат анализа текста: заголовок, нормализованный текст, категория, ведомство, приоритет и обоснование |

Значения RequestStatus: new → under_review → assigned → in_progress → resolved. Это допустимые значения типа, а не принудительная серверная машина состояний: обработчик PATCH не проверяет переходы. Есть 9 категорий, 5 ведомств и 5 районов в объединениях типов. Поля персональных данных и moderation_status являются свойствами CityRequest, отдельные таблицы для них не существуют.

    U[Браузер] --> P[Страницы и компоненты Next.js]
    P --> C[AppContext в браузере]
    P --> A[Route Handlers /api]
    A --> M[mock-data.ts: память серверного процесса]
    A --> I[ai-service.ts]
    I --> G[Gemini при наличии ключа]
    I --> F[Локальные правила fallback]

Диаграмма показывает связи модулей исходного кода, а не гарантирует успешную сборку текущей рабочей копии.

## 4. Страницы и сценарии в коде

| Маршрут | Реализация и ограничение |
|---|---|
| / | Лендинг, демонстрационные показатели, лента и витрина ДО/ПОСЛЕ; данные запрашиваются через /api/requests, при ошибке используются локально импортированные сид-данные |
| /create | Форма проблемы или идеи; FileReader превращает изображение до 15 МБ в data URL; Web Speech API используется при наличии, иначе подставляется пример диктовки; кнопка GPS подставляет фиксированные координаты |
| /map | Компонент Leaflet, маркеры и фильтры; поиск геопозиции устройства есть в CityMap, но это отличается от имитации GPS в форме создания |
| /ideas | Список записей с type=idea и клиентское голосование |
| /requests/[id] | Карточка, таймлайн, голосование и отправка обжалования через PATCH; страница получает данные из mock-data.ts |
| /profile | Клиентская выборка «моих» заявок; если совпадений по автору нет, показываются первые три записи как демонстрационный пример |
| /admin | UI для заявок, статусов, ведомств, приоритетов, модерации, ответов и сообщений разработчикам; проверка роли выполняется на клиенте |
| /analytics | Сводка по сид-данным; допуск сотрудника определяется клиентской ролью, а среднее время разрешения в getRequestStats() задано константой 1.8 |

В коде есть демонстрационный вход по ролям. Текущая форма не сверяет пароль с сервером: для входа сотрудника достаточно непустых полей; пароль жителя не проверяется. Клиент хранит флаги входа и роль в localStorage. Реальной регистрации, сессии, OTP, ЭЦП или серверной авторизации нет.

## 5. HTTP API

| Маршрут | Методы | Фактическое действие |
|---|---|---|
| /api/ai | POST | Анализ текста через Gemini либо локальные правила |
| /api/requests | GET, POST | Список с фильтрами и статистикой; создание обращения |
| /api/requests/[id] | GET, PATCH | Чтение и изменение записи |
| /api/requests/[id]/upvote | POST | Увеличение счётчика голосов |
| /api/requests/similar | POST | Поиск похожих незакрытых обращений по совпадению адресных слов и текста |
| /api/notifications | GET, PATCH | Чтение и отметка уведомления |
| /api/feedback-dev | GET, POST | Чтение и добавление сообщения разработчикам в памяти процесса |

Операции DELETE нет, поэтому API нельзя называть полным CRUD. В create/page.tsx вызывается /api/ai и затем /api/requests; вызов /api/requests/similar из формы не найден. Отдельного внешнего сервиса уведомлений нет: API работает с сид-массивом.

## 6. Границы демо-реализации и риски для отчётов

1. **Авторизация и приватность.** Ограничения страниц реализованы на клиенте, а обработчики API не проверяют личность и роль. GET /api/requests и GET /api/requests/[id] возвращают объект CityRequest целиком, включая необязательные поля автора. Поэтому нельзя писать, что персональные данные защищены серверной RBAC или что доступ к ним имеет только сотрудник.
2. **Сохранение данных.** Это память процесса, не SQL-схема. Любую IDEF1X/ER-модель будущей БД нужно прямо обозначать как проектное предложение, а текущую структуру — как TypeScript-модель и массивы.
3. **Дубликаты и голосование.** Поиск похожих обращений существует как отдельный API, но не доказана интеграция в подачу заявки. Повторный голос блокируется Set/localStorage только в браузерном интерфейсе; серверный POST не проверяет уникальность пользователя.
4. **Геолокация и медиа.** В форме создания GPS имитируется, а на карте браузерная геолокация есть. Изображение кодируется в data URL и хранится с записью в памяти; отдельного файлового хранилища нет.
5. **Показатели и сроки.** avg_resolution_days = 1.8 — константа. Подсветка просрочек в панели не является проверенным регламентом SLA. Демо-фотографии в public/images не подтверждают фактическое выполнение городских работ.
6. **Интеграции.** Связи с 109, e-Otinish, SMS, eGov, электронной подписью и муниципальными информационными системами в коде нет.

Минимальная техническая задача перед практическими, в которых нужен работающий интерфейс: согласовать AppContext с уже использующими его компонентами, затем повторить TypeScript-проверку, lint и сборку. Реализация отложена согласно текущему указанию не менять код.

## 10. Проверка запуска 21 октября 2026 года

По запросу «run site» запущен локальный сервер `npm run dev` на `http://localhost:3000`. Текущая рабочая версия `AppContext.tsx` не предоставляла полей и методов, которые уже используют страницы и компоненты, поэтому браузер падал в `AuthModal` при обращении к `t.authBackToSite`. В контекст возвращены существовавшие в проекте язык, переводы, тема, гостевой режим, состояние входа, профиль пользователя и сигнатуры действий. Сохранены действовавшие в рабочей копии запросы к API уведомлений и форма ответа голосования.

После исправления `npx tsc --noEmit` завершается без ошибок. Браузер открывает главную страницу после демонстрационного гостевого входа, а также страницы `/map`, `/ideas` и `/create`. Проверка подтверждает загрузку и отображение этих экранов в dev-режиме; отправка формы и production-сборка в этот запуск не проверялись. Ранее созданные отчёты отражают состояние на дату их составления, поэтому их разделы о блокирующих TypeScript-ошибках являются исторической записью, а не текущим статусом проекта.
